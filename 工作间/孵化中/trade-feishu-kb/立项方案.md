# trade-feishu-kb 立项方案

## 基本信息

- Skill 名称：飞书知识库承接 Skill
- 建议英文名：`trade-feishu-kb`
- 所属业务节点：课程 / 增强权益 / 知识库索引与同步承接
- 负责人：Codex + Floyd
- 当前状态：可演示前验证中，内部增强优先
- 名称说明：`KB` 是 Knowledge Base 的缩写，在这里指飞书知识库 / wiki，不是飞书 Base 表格

## 业务问题

- 这个 Skill 要解决的具体问题是什么：
  课程正文、作战台、飞书知识库、开源仓库和最终工具库之间容易断链，用户和龙虾需要知道应该读取哪一份、哪些只是入口、哪些属于增强权益。
- 当前人工是怎么做的：
  人工临时找课程目录、飞书页面、作战台说明和本地 Skill 文档，再手动判断是否同步、同步到哪里、如何回读。
- 为什么值得被做成 Skill：
  它能降低课程和作战台资料错配风险，也能把“增强权益不进入公开仓库正文”的边界固定下来。

## 成功标准

- 最小成功结果是什么：
  输入课程源目录和目标飞书入口后，输出课程源映射、入口页结构建议、同步动作建议、权限边界和回读验收点。
- 用户拿到结果后，能直接做什么下一步动作：
  按建议更新索引页，确认哪些内容需要飞书增强入口承接，哪些只需在公开仓库保留边界说明。
- 什么情况下算“做出来了但还不能交付”：
  能列目录，但不能说明权限边界、入口关系和回读验收方式。

## 输入

- 最小输入：
  课程源目录、目标飞书知识库入口、已有索引页或目录规则。
- 可选输入：
  作战台模块名、公开仓库入口、会员权益说明、同步限制、飞书 wiki 节点信息。
- 输入示例：
  见 `examples/minimal-input.json`。

## 输出

- 核心输出：
  课程源映射、入口页结构建议、权限边界、同步动作建议、回读验收点。
- 输出格式：Markdown / JSON
- 输出示例：
  等内部样例跑通后补入 `examples/`。

## 核心规则与边界

- 必须遵守的业务规则：
  仓库只放公开可读入口和边界说明；增强权益正文只认飞书增强入口。
- 哪些信息只能写成推断：
  用户权限状态、飞书页面可见性、未来同步频率。
- 哪些情况必须提示人工复核：
  飞书权限不足、课程源目录不确定、同一内容存在多个版本、公开仓库与飞书增强入口口径冲突。
- 明确不做什么：
  不绕过飞书权限；不把公开仓库写成增强权益正文；不强制企业使用固定 Base 或固定表头；不在未授权情况下写入飞书。

## 依赖与实现方式

- 需要的脚本 / 工具 / API：
  首版可以只输出索引建议；真实写入需使用已授权的飞书同步工具。
- 是否需要联网：
  本地目录映射不需要；飞书回读和写入需要。
- 是面向 Codex、本地脚本，还是 OpenClaw / 龙虾优先：
  首版面向内部 Codex 工作流，后续再判断是否给 OpenClaw 做只读入口。
- 是否需要 `for-openclaw/` 变体：
  暂不需要。

## 课程与内容映射

- 对应课程：
  外贸主动开发课、作战台课程中心、年度会员飞书增强知识库。
- 可讲成什么案例：
  如何让课程、作战台和 Skill 资料不再互相漂移。
- 可衍生什么内容选题：
  开源 Skill 与会员增强权益怎么分层、飞书知识库怎么做入口索引、龙虾应该读取哪一层。

## 验收方式

- 最小测试输入是什么：
  一个课程源目录、一个目标飞书入口页、一个已有或待建索引结构。
- 预期输出应包含哪些关键信息：
  源目录映射、入口页结构、同步动作建议、权限边界和回读验收点。
- 如何判断这个 Skill 已达到可演示：
  能用一个内部样例讲清“本地源 -> 飞书入口 -> 作战台读取口径”的关系。
- 如何判断这个 Skill 已达到可交付：
  至少 2 次同步/回读样例稳定通过，并写清权限失败时的降级路径。
