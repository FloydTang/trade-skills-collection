# trade-mail-group 立项方案

## 基本信息

- Skill 名称：Mail Group / 客群分组开发信 Skill
- 建议英文名：`trade-mail-group`
- 所属业务节点：主动开发触达前的客户分组 / 开发信策略
- 负责人：Codex + Floyd
- 当前状态：可演示前验证中

## 业务问题

- 这个 Skill 要解决的具体问题是什么：
  已经整理出一批客户后，业务员容易直接用同一封开发信群发，导致标题、角度和跟进节奏过于泛化。
- 当前人工是怎么做的：
  人工凭经验把客户粗略分成几类，再临时改开发信；分组依据、复核点和后续节奏经常没有沉淀。
- 为什么值得被做成 Skill：
  它承接 `线索整理 -> 客户背调 -> 开发信` 中间的策略层，能把“批量触达”变成“先分组、再写草稿、再人工确认”。

## 成功标准

- 最小成功结果是什么：
  输入 5-10 条客户名单后，输出 2-4 个可解释的客户分组，并给出每组首封邮件角度、英文标题候选、草稿和第一次跟进节奏。
- 用户拿到结果后，能直接做什么下一步动作：
  人工确认分组是否合理，补齐缺失背调信息，再把确认后的分组交给开发信节点或人工发送。
- 什么情况下算“做出来了但还不能交付”：
  能生成分组和文案，但无法解释分组依据，或把推断写成客户事实。

## 输入

- 最小输入：
  我司产品、目标市场、客户名单、客户行业、国家、来源、背调摘要或备注。
- 可选输入：
  目标客群优先级、禁用表达、品牌语气、报价限制、历史跟进情况。
- 输入示例：
  见 `examples/minimal-input.json`。

## 输出

- 核心输出：
  Mail Group 分组方案、每组共同特征、每组首封邮件角度、英文标题候选、首封草稿、第一次跟进节奏、必须补充的背调信息。
- 输出格式：Markdown / JSON
- 输出示例：
  等最小样例跑通后补入 `examples/`。

## 核心规则与边界

- 必须遵守的业务规则：
  分组依据必须来自输入字段、背调摘要或明确标注的业务假设。
- 哪些信息只能写成推断：
  客户采购意向、决策角色、预算、回复概率、渠道偏好。
- 哪些情况必须提示人工复核：
  客户行业不明、国家市场不明、背调摘要缺失、同一客户可归入多个分组、分组会影响报价或合规表达。
- 明确不做什么：
  不自动发送邮件；不配置 SMTP；不承诺回复率；不把分组推断写成客户事实；不绕过开发信节点的人工复核。

## 依赖与实现方式

- 需要的脚本 / 工具 / API：
  首版先不依赖发信平台；可用本地 Markdown / JSON 规则与 LLM 执行流完成。
- 是否需要联网：
  最小样例不需要；真实样例如果需要补查事实，必须明确来源并交给客户背调节点。
- 是面向 Codex、本地脚本，还是 OpenClaw / 龙虾优先：
  首版优先面向 Codex / OpenClaw 可读执行词。
- 是否需要 `for-openclaw/` 变体：
  样例验证稳定后再决定。

## 课程与内容映射

- 对应课程：
  作战台 V1.5 `Mail Group 专用执行词`、外贸主动开发课开发信章节。
- 可讲成什么案例：
  为什么批量开发信不能直接群发，应该先用客户名单做分组触达策略。
- 可衍生什么内容选题：
  客户名单怎么分组、开发信标题怎么按客群改、第一次跟进节奏怎么设计。

## 验收方式

- 最小测试输入是什么：
  一批 5-10 个客户，至少包含行业、国家、来源和背调摘要或备注。
- 预期输出应包含哪些关键信息：
  分组名称、分组依据、每组角度、英文标题、首封草稿、跟进节奏、缺失信息和人工复核点。
- 如何判断这个 Skill 已达到可演示：
  至少 1 组课程样例能稳定输出结构化结果，并能解释事实、推断和复核项。
- 如何判断这个 Skill 已达到可交付：
  至少 2 组样例稳定通过，并补齐 `SKILL.md`、输出样例、风险边界和默认行为说明。
